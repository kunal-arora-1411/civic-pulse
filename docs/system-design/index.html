CivicPulse, explained without the jargon

A citizen photographs a pothole. Some minutes later a municipal crew knows about it, and every other citizen who reported the same pothole is told it is already being fixed. This page shows every part that makes that happen, and why each one exists.

Layers 1–2 are stateless and replaceable. Layer 3 holds all the rules. Layer 4 exists purely so a slow AI model can never make a citizen wait.

  • One database, many cities Every table is tenant-scoped by row-level security inside Postgres, so "another city sees my data" is blocked by the database, not by remembering to add a filter.
  • The API never touches photo bytes Browsers upload straight into storage with a signed pass. The API only records that the upload happened and verifies it afterwards.
  • Nothing important happens inline Submitting a report returns in milliseconds. Embedding, matching, blurring and notifying all happen on workers.
  • The AI is an advisor, not a judge It may link a report to an existing issue on its own only when it is very sure; everything else becomes a task for a human, and if the AI is down nothing is merged.
02

A pothole's journey, step by step

The same path every report takes. The step number is also the order it really happens in — except step 3, which is optional and happens before submission.

  1. The photo goes straight into storage

    The phone asks the API for a one-time upload pass, then sends the file to storage itself. The API checks the signature later, so a file that was never registered can never become a report's photo. The bucket is private; every read is a signed link that expires.

    POST /media/uploads → PUT to MinIO

  2. An optional hint: what is this a photo of?

    Before submitting, the citizen can ask the AI to guess the category. CLIP compares the photo with the city's own categories. If the guess is confident it is used; if not, the citizen picks from a short list. This is a convenience, not a gate.

    classification, ai queue · threshold is per tenant

  3. The report is written down — and stops there

    The API checks the category's photo rules, turns the pin into an address and a ward, and refuses coordinates outside the city. It writes the report with matching_status = pending, gives it a human reference, and records an audit entry. It deliberately does not know yet whether this is a new problem or a duplicate.

    POST /reports · one transaction · returns immediately

  4. The photo is cleaned up

    A worker decodes it, strips the EXIF metadata (a photo can carry the photographer's GPS history), produces WebP sizes for the list and the detail view, and refuses anything that will not decode or is absurdly large. A public copy exists only after the face check in step 5 has passed.

    worker · default queue

  5. The AI looks at the picture

    CLIP turns the photo into a vector — a long list of numbers that captures "what this scene looks like". YuNet finds faces and they get blurred. A perceptual hash is also computed: a short fingerprint that says "this is literally the same picture", which catches re-uploads and screenshots that a vector score alone would miss.

    ai-worker · queue: ai

  6. Is this the same pothole someone already reported?

    Nearby open issues from the last months are gathered, scored, and sorted. Three things can happen: link silently, ask a human, or start a new issue. This is the most interesting part of the system, so it gets its own section below.

    ai queue · safety net: watchdog on the default queue

  7. How bad is it, and how soon?

    Rules belonging to the city turn the category's fields into a severity and a priority, and every level comes with its reason recorded ("near a school", "three citizens reported it"). A supervisor can override either one, but only with a written reason, and the override is audited.

    priority rules · recomputed when links or statuses change

  8. Humans take over

    Staff see the issue in a queue and on a map. They move it through the city's own status workflow (which transitions are legal is configuration, not code), assign it to the team that covers that category and ward, and the crew works the resulting order and uploads evidence. Citizens following the issue are notified at each move.

    operations · workflow · notifications

  9. Everyone can see what happened

    The reporter gets a timeline; the public gets a page for the issue and a city scorecard; managers get dashboards whose numbers are built from fixed definitions rather than hand-written queries; and the audit trail keeps an append-only record of who did what.

    public · analytics · audit
03

The clever bit: spotting duplicates

Ten people photograph the same broken drain from ten angles. The city should see one issue with a count of ten, not ten tickets. That is what this does.

The system gathers every recent issue of a compatible category within a radius and scores it on four signals. Each signal is a number between 0 and 1, and they are combined with weights the city can change.

  • How close Distance falls off smoothly — a report ten metres away scores far higher than one five hundred metres away. weight 0.40
  • What it looks like The overlap between the two photos' vectors. An identical fingerprint (same file, re-uploaded) counts as a perfect match outright. weight 0.40
  • Same kind of problem Categories the city declared related score higher than unrelated ones — a pothole and a broken footpath may be the same job. weight 0.10
  • How recent Older issues score lower, so a drain fixed last spring does not swallow this summer's report. weight 0.10

The best-scoring candidate decides the outcome. Two thresholds do the work: a high score means act alone, a middling one means ask a person.

  • Link it

    The report joins the existing issue and the reporter count goes up.

    score ≥ 0.85 AND visual ≥ 0.92 AND inside the radius
  • Ask a human

    An operator sees both photos, the score and the signal breakdown, then decides.

    score ≥ 0.60
  • New issue

    Nothing is close enough, so the report opens its own issue.

    everything else

Why not just trust the score? Because a photo alone can be wrong, and a location alone is definitely wrong — two potholes on the same street corner are two potholes. So an automatic link needs both a high overall score and strong visual evidence. Distance by itself can never merge anything.

If the AI worker is down, the visual signal disappears, the score is re-normalised over the remaining three, and the system refuses to auto-link at all — it only opens review tasks above 0.40, or starts a new issue. A duplicate is a nuisance; a wrongly merged report is a lost report.

Two more safeguards: an advisory lock on the location means ten simultaneous identical reports still produce exactly one issue, and a watchdog re-queues any report whose matching never finished, so a crashed worker leaves nothing stranded.

04

Who runs what, and when

Three processes, one clock, and a rule that exists because breaking it silently corrupts data.

Process Queue Does Why it is separate
worker default Photo variants, housekeeping, priority recomputes, matching watchdog Cheap, frequent, must never wait behind a model
ai-worker ai Embeddings, classification, matching, face blur Needs ~1.5 GB of RAM and the models. It is the only consumer of ai, so every vector in the database comes from the same model and scores stay comparable.
beat — Hourly housekeeping · watchdog every minute · nightly priority recompute · weekly matching-quality check Only one may run, or every job fires twice
migrate — Applies database migrations, then exits Runs as the owning role; the API deliberately connects as a lesser role that row-level security actually applies to

The API hands work over by task name, so it never imports the worker code, and a broker that is down only logs an error — the request still succeeds. Every kind of deferred work also has a sweeper, so nothing depends on the enqueue having worked.

05

What gets stored where

Three stores, each doing one job, and one rule about what may be authoritative.

Store Holds Notes that matter
PostgreSQL Cities, users, categories, reports, issues, photos' metadata, match decisions, work orders, notifications, audit The only authoritative copy. Row-level security on every tenant-scoped table; audit rows reject updates and deletes at the database level.
Redis Rate-limit counters, Celery queue All of it is rebuildable; losing it slows things down, never loses a report.
MinIO Original and processed photos Private bucket. Signed URLs change on every request, so browsers cannot cache a photo — a known rough edge, not a bug.
06

Tenants, roles and permissions

One deployment serves many municipalities. A tenant is a city; a role decides what one person in it may do.

Role Can do Cannot do
Citizen Report, support others' reports, track their own, read public pages See any staff view, contact details, internal notes or the audit trail
Operator Work the queue, resolve review tasks, assign and update work orders Change city-wide configuration or manage users
Supervisor Everything an operator can, plus overrides, within their department's scope Reach outside their department's wards and categories
Municipal admin Categories, matching and priority rules, SLA targets, staff accounts, audit Touch another city
Platform admin Create cities and their first accounts Read any city's data — deliberately, so an operator of the platform is not also a reader of citizens' complaints

Under all of this: anonymous requests name their city in a header, signed-in requests get it from their token, and the database re-checks it on every query. Staff accounts also need a second factor; the bypass for that is explicit and scoped, never implicit.

07

Sharp edges worth knowing

Things that look odd until you know why, taken straight from the project's own notes.

Edge Why
Coordinates are [lng, lat] GeoJSON order, everywhere in the API. Getting it backwards puts a Bengaluru pothole in the Arabian Sea.
The ai queue has exactly one consumer Let the ordinary worker drain it and fake and real embeddings get mixed, making every similarity score meaningless.
Perceptual hashes flip sign at the boundary They are unsigned 64-bit values, but Postgres stores them signed. The conversion happens exactly once, where the two meet.
Token refresh must be single-flight Refresh tokens rotate, and reusing one revokes the session. Two parallel refreshes log the user out.
Reports are rate-limited globally, not per city A known gap: the limits are settings, so they cannot be tuned per tenant without a new config key.
SMS still goes out inside the request Fine while volumes are low; a queued outbox is planned rather than built.
08

Plain-English glossary

If you only take eight words away from this page, take these.

Tenant
One city using the platform. Everything stored belongs to exactly one.
Row-level security
A Postgres feature: the database itself refuses to return rows belonging to another city, even if the query forgot to filter.
Presigned URL
A temporary link that grants one upload or download without exposing any credential.
Embedding
A list of numbers representing what a photo looks like, so two photos can be compared by arithmetic.
Perceptual hash
A 64-bit fingerprint of an image. Two hashes that are nearly equal mean nearly the same picture.
Celery
The job queue. The API drops a named task into Redis; a worker picks it up and runs it.
Idempotency key
A client-supplied code that makes a repeated POST return the original answer instead of creating a second report.
Advisory lock
A database-level "I am working on this spot right now" marker, so simultaneous duplicate checks cannot both decide to create an issue.
